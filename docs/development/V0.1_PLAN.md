# Blackglass v0.1 Development Plan

Status: working v0.1 plan, CTF-ready program

Program goal: a workbench that can operate a real CTF box end to end.

Working today: the engagement, target, and Nmap loop with lifecycle polling, XML evidence publication, projected services with download links, archive and reopen, and saved scope.

Deferred placeholders: the console Advisor, Activity, and Raw output tabs; settings controls await the settings store; plugins await the D5 protocol gate.

Next slices, in order: engagement notes, HTTP probing, findings capture, raw run output viewing, engagement deadlines. See section 13.

## 1. Product outcome

Blackglass is a fast, local-first, open-source security workbench for CTFs, labs, and operator-authorized assessments.

The v0.1 release targets one complete workflow:

```text
engagement
  -> targets and optional scope guardrails
  -> Nmap discovery
  -> HTTP probing
  -> ffuf discovery
  -> evidence
  -> findings and analyst records
  -> report
  -> local AI advisor
```

The product is single-user and runs on Linux. It is optimized for moving quickly through an assessment. Scope and risk metadata organize targets, warnings, evidence, and reports while every representable action stays runnable.

## 5. Core domain model

### Engagement

An engagement represents one CTF box, lab, or assessment. It records identity, description, type, lifecycle status, optional authorization/context notes, active saved-scope revision, and created/updated timestamps. Engagements can be archived and reopened.

### ScopeRevision and ScopeRule

Scope revisions are immutable snapshots of the operator's saved target context. They drive filtering, suggestions, warnings, and reports. Every representable action remains runnable. Supported rules cover:

- IPv4 and IPv6 addresses;
- CIDRs;
- domains with an explicit subdomain policy;
- URL origins;
- optional port restrictions.

Every action records its exact resolved target set, options, saved-scope revision when present, and any warning acknowledgment. A retry starts from the prior run's target/options snapshot unless the operator edits it.

### Asset and Service

Normalized discovery records include:

- asset address or hostname and provenance;
- DNS resolutions and resolution-time evidence;
- open port, protocol, service, product, and version;
- HTTP origin, status, title, selected headers, TLS metadata, and redirect chain.

### Action and Run

An `Action` is an intended operation. A `Run` is one execution attempt.

```text
queued -> leased -> running -> succeeded | failed | cancelled
```

Terminal transitions occur once. Expired leases and late events are rejected deterministically. Retrying creates a new run and never mutates prior evidence.

Supported reverse operations include:

- cancel a queued or running run;
- retry a failed or cancelled run;
- archive and reopen an engagement;
- resolve and reopen a finding;
- disable and re-enable a plugin.

### EvidenceArtifact and Observation

Evidence is content-addressed using SHA-256.

- Raw output and machine-readable output are separate artifacts.
- The control plane generates every artifact path.
- Existing raw evidence stays immutable across runs and parser updates.
- Observations reference their plugin, run, artifact, and relevant evidence position.
- Partial evidence remains available after cancellation or failure and is labelled truthfully.

Owner retention and deletion use a separate documented operation.

### Finding and analyst records

A finding records title, severity, confidence, status, affected entities, technical description, impact, remediation, evidence references, and provenance. Provenance is deterministic, model-assisted, or user-authored.

Model-generated findings begin as drafts and require confirmation.

Planned engagement records, arriving across slices S1, S3, and later scope: Markdown notes, masked flags, an activity timeline, and reports with engagement context, saved scope, executive summary, methodology, attack surface, findings, remediation, limitations, objectives, timeline, and evidence appendix.

Exports are JSON, Markdown, and print-ready HTML. PDF uses browser Print to PDF rather than a bundled server-side browser.

## 6. Target context, warnings, and execution

The operator controls what runs. Saved scope provides context and warnings.

Saved scope exists to make target selection, filtering, evidence provenance, and reporting useful. When an action includes a target outside the saved scope, the control plane returns a normalized warning context and the UI offers:

- `Continue`: queue the exact action without changing saved scope;
- `Add to scope & run`: create a new saved-scope revision and queue it;
- `Cancel`.

`Continue` is always available. The warning is acknowledged once for the action, not once per target, DNS answer, or redirect hop. The acknowledgment covers destinations discovered by that run and records their actual normalized values in events/evidence. The operator may configure an engagement to auto-continue warnings for faster CTF use.

Validation errors are reserved for malformed inputs that the system cannot represent or execute.

### Informational risk tiers

- **T0:** local reads, parsing, and reporting; no warning.
- **T1:** routine discovery; no warning by default.
- **T2:** noisy or intrusive enumeration such as ffuf; one concise warning by default.
- **T3:** exploit or credential use supplied by a future/local plugin; one prominent warning by default.
- **T4:** destructive or irreversible behavior supplied by a future/local plugin; one prominent warning by default.

Risk tiers select copy, defaults, and visual emphasis. Every declared tier uses the same runnable action path. First-party v0.1 tools cover T0 through T2.

The runner starts an explicit executable with an argv array. This keeps command construction predictable and protects the host from accidental shell injection.

Exact normalization, warning acknowledgment, DNS/redirect recording, idempotency, concurrency, and retry semantics must be accepted before their dependent milestones. See [`../architecture/DECISION_GATES.md`](../architecture/DECISION_GATES.md).

## 7. Runner model

The host runner executes selected actions and leaves target, purpose, and risk decisions to the operator.

The v0.1 runner requires:

- explicit first enrollment and owner confirmation;
- a dedicated identity and least-privilege API surface;
- token generation, hash/storage, rotation, revocation, recovery, and redaction rules;
- control-plane/runner protocol handshake;
- lease, heartbeat, expiry, fencing, and replay protection;
- an installed-plugin executable registry where the operator may configure any local executable;
- minimal predictable environment and controlled working directory;
- operator-configurable time, output, resource, and concurrency controls, including unlimited modes where the host can support them;
- argv-only process spawning;
- process-group cancellation with escalation deadlines;
- bounded stdout/stderr streaming with backpressure;
- safe artifact staging, hashing, and atomic publication;
- path, symlink, and hardlink defenses;
- truthful partial evidence.

The fake action contract suite proves the complete runner lifecycle before a real tool is connected.

## 8. Plugin protocol

Status: deferred until decision gate D5. No plugin SDK ships yet and no `plugins/` directory exists. The text below is the planned protocol, not shipped behavior.

Plugins are separate processes and may be implemented in Python, Go, Rust, or TypeScript.

Each plugin has a versioned `plugin.json` manifest describing:

- stable plugin ID, plugin version, and protocol version;
- display metadata;
- entrypoint and required external binaries;
- commands and JSON Schema inputs;
- informational risk tier and declared host requirements;
- emitted observations, artifacts, forms, and report sections.

Runtime communication uses versioned NDJSON over stdin/stdout. Input contains action/run IDs, the resolved target set, saved-scope context, limits, and typed options. Output supports:

- `log`;
- `progress`;
- `artifact`;
- `observation`;
- `completed`;
- `error`.

Plugins contribute schema-driven forms, result panels, and report sections.

Local-path installation validates the manifest and protocol, rejects path and symlink escapes, copies an immutable digest-pinned version into managed storage, shows declared host requirements, and asks for one confirmation. Updates use the same explicit reinstall flow. Removal or disabling preserves prior evidence provenance.

The protocol is proven by first-party adapters before it is presented as a stable community SDK.

## 9. First-party workflows

### Nmap

Working today:

- XML is the parser contract.
- The initial profile is a practical, configurable TCP connect and service discovery profile optimized for fast CTF use.
- Raw XML and stderr are preserved separately.
- Privileged scan modes become available whenever the runner and selected executable are configured to support them.
- Cancellation terminates the process group and preserves partial evidence.

### HTTP probe

Status: next slice S2, not built yet. Planned behavior:

- Implemented as a first-party adapter.
- Probes resolved HTTP/HTTPS targets selected by the operator.
- Captures status, title, selected headers, TLS metadata, and redirect chain.
- Redirect hops are recorded and compared with saved scope. A run-level warning acknowledgment allows the chain to continue without repeated prompts.

### ffuf

Status: later v0.1 slice, not built yet. It awaits the D5 protocol gate for plugin installation. Planned behavior:

- Requires a configured local binary and wordlist.
- Receives normalized origins selected by the operator.
- Uses JSON output as its parser contract.
- Provides editable rate, concurrency, timeout, and duration defaults; the operator may raise or disable them.
- Is labelled T2 and shows at most one concise pre-run warning unless the engagement is configured to auto-continue.
- Plans to ship only a tiny synthetic test wordlist; production wordlists are user-managed.

A planned `blackglass doctor` will verify supported tool versions, permissions, runner connectivity, evidence storage, and model endpoint health. It is not built yet.

## 10. Local advisor

Status: deferred until decision gate D6, not built yet. The console Advisor tab is a placeholder until then. The text below is the planned design, not shipped behavior.

The configurable model profile contains a base URL, model ID, optional API-key environment-variable name, timeout, context limits, and connection test.

Local and private endpoints work by default. Public endpoints show a data-sharing warning and one-click opt-in. API keys are resolved from environment variables at request time.

Modes:

- **Operator:** concise evidence and next actions; the default.
- **Mentor:** explains findings, evidence, risk, and expected results.

The model receives inspectable capabilities such as:

- `get_engagement`;
- `list_assets`;
- `list_observations`;
- `read_evidence_excerpt`;
- `list_available_actions`;
- `run_action`;
- `propose_action`;
- `draft_finding`;
- `draft_report_section`.

Advisor capabilities use the same orchestrator and warning path as human actions. T0 and T1 actions may start immediately. T2, T3, and T4 actions use the same single `Continue` card as the rest of the product. Any installed plugin action may be exposed to the advisor. Model conclusions and raw responses remain visible to the operator.

Tool-call, run, elapsed-time, context, request, response, and output controls are operator-configurable, with practical defaults and an unlimited mode where technically possible. Plugin and evidence content is marked untrusted. Responses contain evidence references, confidence, assumptions, recommended actions, and explicit abstention when evidence is insufficient. Invalid structured output is shown as a truthful parse error with retry/raw-response options rather than silently discarded.

The exact provider compatibility profile, data classification, endpoint threat model, retention, cancellation, and audit metadata are decided before advisor implementation.

## 11. UI constitution

The UI is implemented independently from reference products.

Global navigation contains Dashboard, Engagements, Plugins, and Settings. Engagement navigation contains Overview, Surface, Runs, Findings, Evidence, Notes, and Report.

The bottom console contains Advisor, Activity, and Raw output. All three tabs are deferred placeholders: Advisor awaits gate D6, Raw output arrives with slice S4, and Activity fills in as run event work lands. It defaults to 320 px, resizes between 220 px and 60% of viewport height, collapses to a status bar, persists height locally, and becomes a full-screen sheet on mobile.

The desktop sidebar defaults to 256 px, has a 208 px minimum, is limited by a 640 px content remainder, and supports full off-canvas collapse. It becomes a full-width modal sheet on mobile. Width and open state are restored before first paint. Resize updates are frame-bounded and do not animate continuously.

Visual rules:

- emerald workspace brand at hue 145;
- cooler pine/teal navigation at hue 168;
- `oklch(0.55 0.18 145)` light primary;
- `oklch(0.78 0.21 145)` dark primary;
- semantic success, info, warning, and destructive roles;
- components consume semantic color tokens;
- 10 px base radius;
- 12 px glass blur only for transient overlays;
- system theme by default with light and dark overrides;
- technical identifiers use JetBrains Mono.

Interaction rules:

- active, selected, hover, and status are distinct;
- status combines color with text or iconography;
- spinners appear only for real pending work;
- lifecycle actions expose their supported reverse action;
- touch targets are at least 44 by 44 px;
- hover actions are keyboard- and touch-accessible;
- bounded list changes use 150 ms ease-out motion;
- reduced motion disables list animation, shimmer, and nonessential transitions;
- loading preserves the stable shell;
- empty, filtered-empty, stale, recoverable-error, and fatal-error states are distinct.

The detailed interaction contract lives in [`../ui/constitution.md`](../ui/constitution.md). The first UI issue implements its tokens and component gallery before domain pages.

## 12. API surface

Public routes are versioned under `/api/v1`. Planned resources include:

- system health and status;
- engagements and archive/reopen lifecycle;
- scope revisions;
- assets and observations;
- actions, warning context, and continuation;
- runs, cancellation, retry, and event streams;
- evidence download;
- findings;
- advisor messages and streams;
- reports and exports;
- plugins and staged installation.

Runner-only endpoints use a separate identity for leasing, heartbeat, event append, and terminal transitions.

Contracts originate in `packages/contracts` and every client imports them. Commands that can be retried require explicit idempotency semantics. SSE defines event IDs, retention, resume, and expired-cursor behavior before implementation.

## 13. Milestones

Each milestone groups focused PRs and ends in an observable clean-state scenario.

Status: M0 through M4 are done and working. M4 is the first useful installable slice. Next is the CTF-ready sequence S1 through S5, taken in order. ffuf discovery, the local advisor, and release work follow after.

### M0: Governed repository

Done. Establish the AGPL repository, canonical documentation, issue/PR templates, pinned tool versions, lint/type/test/build commands, baseline CI, and available branch protection. Prove the workflow with one deliberately tiny PR.

### M1: Executable shell

Done. Start the web/API locally from a clean checkout, use an isolated development data directory, expose health/status, and deliver the responsive shell, tokens, component gallery, loading, empty, and error states.

### M2: Engagement and target context

Done. Create, archive, and reopen engagements; create versioned saved-scope snapshots; normalize supported targets; compare actions with saved scope; persist one-click warning acknowledgments; expose API routes and minimal target UI; prove that `Continue` always queues a representable action.

Decision Gate D1 is required first.

### M3: Safe runner

Done. Enroll a runner and execute a fake action through lease, stream, cancellation, retry, failure, and partial-evidence paths. Reject expired/late events and prove argv, environment, output, process, and storage defenses.

Decision Gates D2 and D3 are required first.

### M4: Nmap vertical slice

Working today. From a clean dedicated lab, create an engagement and saved scope, execute a configurable Nmap action, follow it through lifecycle polling, cancel and retry it, preserve XML evidence, parse observations, and display projected services with download links. An outside-scope target produces one warning and then runs when the operator continues.

M4 is the first useful installable slice and the earliest point at which a nightly channel may add value. The owner reviews the working architecture before continuing.

### CTF-ready sequence

Take these in order. S2 supersedes the old M5 HTTP surface milestone. S1 and S3 take the notes and findings parts of the old M7 analyst record; its timeline, masked flags, and reporting parts stay in later scope.

#### S1: Engagement notes

Markdown notes scoped to one engagement and editable across sessions.

Acceptance: an operator can write, edit, and reload engagement notes without losing content.

#### S2: HTTP probing

Probe discovered HTTP services and record status, title, selected headers, TLS metadata, and redirect hops with raw evidence preserved.

Acceptance: probing a discovered service projects its HTTP observations and preserves the raw evidence.

#### S3: Findings capture

Promote runs into findings with notes and evidence references.

Acceptance: an operator can record a finding against a run with attached notes and evidence references.

#### S4: Raw run output viewing

Open the preserved raw stdout and stderr of a run from the engagement workspace. This fills the console Raw output placeholder.

Acceptance: an operator can view the exact preserved raw output of a finished or cancelled run.

#### S5: Engagement deadlines

Set an optional deadline on an engagement, surfaced in the workspace.

Acceptance: an operator can set a deadline on an engagement and see it in the workspace.

### Later v0.1 scope

#### M6: Fast ffuf discovery

Deferred until the D5 protocol gate for plugin installation. Configure, continue/cancel, execute, stop, and retry T2-labelled discovery. Apply operator-selected binary, wordlist, rate, concurrency, and duration settings; show at most one warning and preserve complete target/evidence context.

#### M7: Analyst record remainder

Deferred. Timeline display, masked flags, evidence excerpts, and JSON, Markdown, and safe print HTML export. Notes and findings capture arrive earlier as S1 and S3.

#### M8: Local advisor

Deferred until decision gate D6. Configure an OpenAI-compatible endpoint, exercise Operator and Mentor modes, invoke any enabled typed plugin capability, use the shared one-click warning flow, honor operator-configured resource controls, cite evidence, and abstain when evidence is insufficient.

#### M9: Release candidate

Deliver the Compose control plane, native runner service, installer/doctor path, consistent backup and restore, migration rehearsal, accessibility review, security audit, and clean-install acceptance on supported Linux hosts.

#### M10: Public v0.1

Complete dependency/license review, checksums, SBOM, disclosure documentation, plugin example, demo recording, changelog, and owner-approved signed release from reviewed `main`.

Decision Gate D7 is required first.

## 14. Acceptance baseline

Domain and security tests cover malformed/ambiguous targets, saved-scope comparison, one-click continue and auto-continue, DNS/redirect recording, every risk tier remaining runnable, argv injection, shell execution, paths, symlinks, artifact overwrite, unknown events/schema versions, and secret redaction.

Runner tests cover lease fencing, expiry, replay, large bounded output, cancellation, timeout, partial evidence, retries, and truthful missing-tool errors.

Advisor tests cover native tool calling and strict-JSON fallback, undeclared capabilities, shared warnings and continuation, evidence citations, abstention, malicious evidence content, budgets, cancellation, and key redaction.

UI acceptance covers desktop/mobile, light/dark, reduced motion, keyboard-only use, responsive resizing, persistence, lifecycle reverse operations, warning continuation/cancellation, and distinct loading/empty/stale/error states.

On a clean supported Linux host, v0.1 is accepted when the owner can start the control plane and runner, pass `blackglass doctor`, configure a model endpoint, complete the workflow from engagement through report, continue an outside-scope action with one click, and archive/reopen the engagement without touching unrelated owner data.

## 15. Defaults

- Supported hosts: Ubuntu 22.04/24.04 and Kali Linux on x86-64.
- Native development is supported on the current 4 GiB LXC host; model inference runs elsewhere.
- Loopback-only binding is the default.
- v0.1 stores SQLite and evidence as plaintext protected by filesystem permissions and documented backup/restore.
- Operator is the default advisor mode; Mentor is one action away.
- Nightlies begin no earlier than the first installable M4 slice and are built only from reviewed `main`.
